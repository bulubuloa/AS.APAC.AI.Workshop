Learning outcomes and tool choice

Participants will connect an emulator, use Android resource IDs, run the login checks and understand the vehicle/OTP/dashboard workflow. Appium with UiAutomator2 controls the native Android app; WebdriverIO organizes tests and assertions. Playwright is used for the browser workshop. Espresso can suit developer-owned Android instrumentation, and Maestro can suit concise mobile flows; this workshop does not contain a controlled comparative benchmark.

This project locks Appium 2 and WebdriverIO 9 dependencies. Use npm ci and the project README rather than upgrading to the latest major during the lab. Appium installation concepts; WebdriverIO 9 documentation.

Prepare the device and example project

Prerequisites: Node and Git, Android SDK/platform tools, a configured emulator, a project-compatible JDK and an approved UAT APK. Set ANDROID_HOME / ANDROID_SDK_ROOT and JAVA_HOME to your actual Windows installations. The APK and local .env are intentionally outside source control. Populate only the variable names in the project template with approved credentials.

git clone https://github.com/bulubuloa/AS.APAC.AI.Workshop.git
cd AS.APAC.AI.Workshop/roadside-android
npm ci
adb devices
adb install -r apk/app.apk
npm test
npm run report

The default device is emulator-5554 and package is com.aspire.partner.uat. Confirm both match your installation. The configuration uses one instance, UiAutomator2 and a 180-second Mocha timeout. It can start Appium automatically. If startup is slow, use the two-terminal alternative:

# Terminal 1
npm run appium
# Terminal 2, PowerShell
$env:APPIUM_EXTERNAL='1'
npm test

Example project and selector exercise

Read wdio.conf.ts, pages/ids.ts, LoginScreen and OtpScreen before editing tests. Current source resource IDs are the authority: policy_accept_button exists in the current implementation even though older README discussion describes a text-only consent locator. Use IDs instead of coordinate taps whenever available.

const submit = $('android=new UiSelector().resourceId("' + resourceId + '")');
await submit.waitForDisplayed();
await expect(submit).toBeEnabled();

Suggested AI prompt: “Read the login and OTP Page Objects and existing specs. Add an assertion for the approved invalid-login scenario using current resource IDs. Reuse setup, do not send extra OTP requests, and explain what the assertion proves. Run only the selected spec with approved UAT fixtures.”

Participants should check that invalid credentials do not enter the dashboard and that the expected error is shown. The exact error text must come from the approved requirement or observed application contract, not an AI guess.

Fresh OTP flow and its integration boundary

The full saved scenario accepts policy, signs in, selects a vehicle, fills driver name and a valid ten-digit test mobile, requests OTP, reads a newer authorized UAT SMS record, enters the code and verifies MainActivity/bottom navigation. Record the latest SMS identifier before requesting OTP to avoid reusing an old code.

const baseline = await latestSmsId();
// Use the existing Page Object to request OTP for the approved fixture.
const otp = await waitForOtp(baseline);
// Enter otp through the existing Page Object, then assert dashboard navigation.

The UAT /api/pmws/smslatest endpoint requires provider authentication and the UAT test feature flag. The test phone must be a dedicated approved number. A real OTP request may send SMS. Reading the backend SMS record proves that this integration generated a retrievable code; it does not prove delivery to a physical handset. Raw SMS logs, phone numbers and provider credentials must stay out of shared evidence. The OTP code sample in slide 8 clips its final line; use the repository helper and the complete flow described here.

Pipeline plan and lab completion

Proposed mobile CI: provide approved APK to boot and verify emulator to start compatible Appium/UiAutomator2 to preflight account/vehicle/OTP endpoint to run selected WDIO pack to reject missing, failed or unexpectedly skipped tests to retain sanitized reports and failure screenshots. Keep a separate physical-device release check for permissions, camera, GPS, network behavior and SMS delivery. This pipeline is proposed, not deployed.

A participant finishes when the approved selected test has a meaningful pass/fail assertion, its device/app configuration is recorded, and sanitized evidence is readable. Review every AI-generated change before merging; neither an AI-written test nor a green UI assertion proves all backend integrations.
