Decision: use Playwright Test for RoadSide and Benefit web end-to-end testing; retain Appium with WebdriverIO for the native Aspire Partner Android app. Playwright fits our popup workflows, report requirements and existing TypeScript examples, with no framework license fee. The POC demonstrates useful checks and evidence capture; it does not establish that Playwright is universally faster or cheaper than every alternative.

3. Examples: the same intent, different authoring approaches

The web examples below express “open a test vendor detail and assert its expected name.” Selectors and URLs are illustrative and must be adapted to the application. These alternatives have not been executed in our environment. The Playwright repository example is separately linked as measured POC evidence. No credentials are embedded.

Playwright: direct browser assertions and popup handling

import { test, expect } from '@playwright/test';
test('vendor detail matches fixture', async ({ page }) => {
  await page.goto(process.env.TEST_VENDOR_DETAIL_URL!);
  await expect(page.getByLabel('Vendor Name')).toHaveValue('QA Vendor');
});
// RSA: capture the popup before the click.
const popup = page.waitForEvent('popup');
await page.getByRole('link', { name: dealerName }).click();
const detail = await popup;
await expect(detail.locator('#dealerName')).toHaveValue(dealerName);

Useful here: assertions retry while the page settles, and a new tab remains a first-class page. Our actual RSA test compares code and name through Page Objects: TC02.2 source. Official popup/page model; actionability and waiting.

Selenium: explicit waits and window handles

from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

driver.get(test_vendor_detail_url)
field = WebDriverWait(driver, 10).until(
    EC.visibility_of_element_located((By.ID, 'vendorName')))
assert field.get_attribute('value') == 'QA Vendor'

Useful here: reuse an established language/test-runner/Grid ecosystem. For RSA, collect window handles, wait for the new window and switch before asserting. We prefer Playwright’s integrated runner and evidence for this new web project; Selenium can achieve the same business checks with suitable libraries. Official window handling example.

Cypress: concise single-tab form/detail check

it('vendor detail matches fixture', () => {
  cy.visit(Cypress.env('TEST_VENDOR_DETAIL_URL'));
  cy.get('[data-testid=vendor-name]')
    .should('have.value', 'QA Vendor');
});

Useful here: interactive browser debugging and retrying command assertions. For a new-tab dealer journey, use the documented Puppeteer plugin or a single-tab adaptation; removing a link’s target changes what is tested. Playwright handles our existing popup without that adaptation. Official Cypress trade-offs. Cypress remains a credible choice for single-tab/component-heavy teams.

7. Decision and next validation

Adopt Playwright for new RSA/Benefit web checks and retain Appium/WDIO for native mobile. Keep tests and evidence in the repository, start with the required POC pack and publish sanitized artifacts through the proposed pipeline. Do not buy a cloud dashboard solely to execute the initial web suite.

If procurement needs a competitive benchmark, run the same fixture-controlled workflows in Playwright, Selenium and Cypress: dealer popup, dependent vendor form, file upload, save/detail/CMS and negative validation. Measure implementation/review time, clean-run duration, failures across repeated runs, diagnosis time and infrastructure cost. Include legitimate business failures rather than hiding them through retries. This benchmark is future work, not evidence already collected.
